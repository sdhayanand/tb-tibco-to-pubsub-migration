# Concept mapping: TIBCO EMS / BusinessWorks / IBM MQ → Google Cloud Pub/Sub & GCP

> Companion to `ARCHITECTURE.md` §7 and `RUNBOOK.md`. Every row answers the same three
> questions: *what did we have, what is the closest GCP thing, and where does the analogy break.*
> The "gotcha" column is the part that bites you in production — read those even if you skip the rest.

## 0. The one-paragraph version

TIBCO EMS and IBM MQ are **queue-centric brokers**: a destination is a durable, ordered,
transactional buffer that one consumer group drains. Pub/Sub is **topic-centric**: a topic is a
log, every *subscription* is an independent cursor into it, delivery is at-least-once, ordering
is opt-in and per key, and there are no broker-side transactions. Almost every migration problem
is a consequence of those differences: queue → topic+subscription, selectors → attribute filters,
XA → outbox + idempotency, priority → separate topics, browse/replay → seek/snapshot/BigQuery.

## 1. Messaging primitives

| TIBCO EMS / JMS | IBM MQ | Pub/Sub equivalent | Gotchas & what this repo does |
|---|---|---|---|
| **Queue** (`TB.ORDERS.OUT`): point-to-point, one message → one consumer, competing consumers | Local queue | **Topic + one pull subscription** shared by the consumer deployment. Competing consumers = several subscriber clients on the *same* subscription. | A subscription is a *cursor*, not a buffer you can look into. If you create a topic without a subscription, messages are dropped on the floor (no subscription = no retention). Terraform creates subscriptions *before* producers go live. |
| **Topic** (pub/sub, non-durable subscriber) | Topic string / topic object | Topic + one subscription **per consumer**. | Pub/Sub has no non-durable subscribers: every subscription retains until acked or expired (`message_retention_duration`, default 7 d, max 31 d). Idle subscriptions auto-delete after `expiration_policy.ttl` (default 31 d) — set `ttl = ""` for subscriptions that must survive quiet periods (DR, seasonal). |
| **Durable subscriber** (`clientId` + subscription name on a topic) | Durable subscription (`DEFPSIST`) | A named subscription. Every Pub/Sub subscription is durable. | EMS durable subscribers are tied to one `clientId`; Pub/Sub subscriptions can be pulled by many clients at once (competing consumers for free). The `jms-to-pubsub-bridge` supports `JMS_SOURCE_TYPE=topic` + `JMS_CLIENT_ID`/`JMS_DURABLE_NAME` so it can drain an EMS topic without missing messages while it is restarted. |
| **Shared durable subscription** (JMS 2.0) | — | Same as above (one subscription, N subscribers). | Nothing to do — Pub/Sub is "shared" by default. |
| **Message selector** (`storeId IN ('0412') AND eventType = 'ORDER_CREATED'`) — SQL-92 over headers *and* properties, evaluated per consumer | Selectors (JMS) / `MQGET` match options (`MsgId`, `CorrelId`) | **Subscription filter** (`attributes.source != "TIBCO_EMS_BRIDGE"`, `hasPrefix(attributes.storeId, "04")`) | Filters see **attributes only — never the payload** — and are **fixed at subscription creation** (change = recreate subscription). Only `=`, `!=`, `hasPrefix`, `AND/OR/NOT`, no `IN`, no numeric comparison. Everything a consumer may filter on must be an attribute, which is why every publisher sets `eventType`, `storeId`, `source`, `schemaVersion` (ARCHITECTURE §3.1). Filtered-out messages are acked by the service and are **still billed**. |
| **Message properties** (typed: `String`, `int`, `boolean`…) + standard headers (`JMSMessageID`, `JMSCorrelationID`, `JMSTimestamp`, `JMSExpiration`, `JMSPriority`, `JMSReplyTo`, `JMSRedelivered`, `JMSXDeliveryCount`) | MQMD fields (`MsgId`, `CorrelId`, `PutDate`, `Expiry`, `Priority`, `ReplyToQ`, `BackoutCount`) + MQRFH2 folder for JMS properties | **Attributes** (string → string, ≤ 256 B key, ≤ 1024 B value, ≤ 100 per message) + system fields `messageId`, `publishTime`, `orderingKey`, `delivery_attempt`. | Attributes are **strings only** — type information is lost (`HeaderMapper` keeps them as strings; consumers parse). `JMSMessageID` ≠ Pub/Sub `messageId`: the bridge carries the JMS id as `legacyMessageId` for de-dup and the Pub/Sub id back as `pubsubMessageId`. IBM MQ: a JMS producer adds the MQRFH2 header; non-JMS MQ consumers choke on it → send with `queue:///ERP.ORDERS.IN?targetClient=1` (`JMS_DESTINATION`). |
| **Message body types**: `TextMessage`, `BytesMessage`, `MapMessage`, `ObjectMessage`, `StreamMessage` | `MQSTR` / `MQHRF2` / binary formats (`MQFMT_*`, CCSID conversion) | Opaque `data` bytes (+ optional **topic schema**: Avro or protobuf, JSON or binary encoding). | Only `Text`/`Bytes` map 1:1; `MapMessage`/`ObjectMessage` must be re-serialized (the bridge treats them as poison → DLQ). Topic schemas validate every publish — a schema rejects `null` fields in proto-JSON, hence `@JsonInclude(NON_NULL)`. Schema *revisions* are additive only; a breaking change is a new topic (`orders-v2`). |
| **Message size**: EMS up to 512 MB (configurable), MQ up to 100 MB (`MAXMSGL`) | | **10 MB** per message (data + attributes), 10 MB per publish batch. | **Claim-check**: big payloads (custom-suit CAD files, EDI batches) go to GCS, the message carries the `gs://` URI + checksum; consumer reads the object. Do it in the bridge for `TB.TAILORING.WO` attachments. |
| **Persistent vs non-persistent delivery** (`DeliveryMode`), `JMSExpiration` / TTL per message, EMS `expiration` per destination | `Persistence`, `Expiry` (tenths of a second) | Everything is persistent & replicated (3+ zones). TTL only at **subscription** level: `message_retention_duration` (10 min – 31 d) and topic-level `message_retention_duration` (for seek). | There is no per-message TTL. A "this coupon expires in 5 min" semantic must be an attribute (`expiresAt`) the consumer checks. Non-persistent/fast-path messages: there is no cheaper mode — Pub/Sub cost is per byte, not per durability. |
| **Priority** (`JMSPriority` 0–9; EMS honours it per queue) | `Priority` 0–9 (queue can be `MSGDLVSQ(PRIORITY)`) | **Not supported.** | Model priority as **separate topics/subscriptions** (`orders-v1` vs `orders-expedite-v1`) with separate consumers / larger flow-control, or as an attribute the consumer uses to pick a worker pool. Nothing reorders within one subscription. |
| **Redelivery**: rollback / recover → broker redelivers, `JMSRedelivered`, `JMSXDeliveryCount`; EMS `maxRedelivery` per destination → `$sys.undelivered` | `BackoutCount`, `BOTHRESH` + `BOQNAME` (backout queue) | `nack()` or ack-deadline expiry → redelivered; **`delivery_attempt`** (only when a dead-letter policy exists); subscription **retry policy** (immediate or exponential backoff 10 s–600 s). | Redelivery is also triggered by *slow* consumers (ack deadline, default 10 s, extended automatically by the client library up to `maxAckExtensionPeriod`). Duplicates are normal (at-least-once) — consumers must be idempotent (`inbox` table, `legacyMessageId`/`eventId` key) or use **exactly-once delivery** subscriptions (ordering + `ackWithResponse()`, higher latency, pull only). |
| **Dead-letter queue**: EMS `$sys.undelivered`, MQ `DLQ` / backout queue | `SYSTEM.DEAD.LETTER.QUEUE` | **Dead-letter policy** on the subscription: after `max_delivery_attempts` (5–100) forward to a DLQ *topic* (`events-dlq`) which needs its own subscription (`events-dlq-monitor`) and IAM (`pubsub.publisher` + `subscriber` for the Pub/Sub service agent). | The DLQ is a topic → it also needs a subscription or messages vanish. Payload is forwarded untouched; original attributes + `CloudPubSubDeadLetterSourceDeliveryCount` etc. are added. Pipeline-level poison (unparseable XML) is published to the same topic by the bridges with `dlqReason`/`dlqStage` (ARCHITECTURE §3.4). |
| **Transactions**: local JMS tx (`session.commit()` = all sends + all acks atomic), **XA / 2PC** across EMS + Oracle via BW or an app server | Local syncpoint, XA (MQ as resource manager) | **None.** Publish is atomic per message (batch publish is *not* atomic), ack is per message. | Replace XA with (a) **transactional outbox** (write business row + outbox row in one DB tx, relay publishes; ARCHITECTURE §5.1), (b) **idempotent consumers** / inbox table, (c) **exactly-once subscriptions** where duplicates are intolerable. The bridges use a *local JMS transaction* + "wait for Pub/Sub ack before commit" = at-least-once with a tiny duplicate window, de-duplicated by `legacyMessageId`. |
| **Request/reply** (`JMSReplyTo` + temporary queue + `JMSCorrelationID`, EMS/BW "Request-Reply" activities) | `ReplyToQ` / `ReplyToQMgr`, `MQRC`-style sync calls | No temp queues. Options: **reply topic + `correlationId` attribute** (reply consumer filters/joins), or — usually better — a **synchronous REST/gRPC call** (Cloud Run / GKE behind Apigee). | Pub/Sub latency floor (~100 ms p50, seconds under backlog) makes it a poor RPC bus. In this platform all request/reply (OMS `GetOrderStatus`, inventory check) moved to REST; messaging is for events. Temporary queues do not exist; creating per-request subscriptions is slow (seconds) and quota-limited (10 000 subscriptions/topic). |
| **Ordering**: strict FIFO per queue (single consumer) / per producer-session; EMS *exclusive* queues; MQ message groups (`GroupId`, `MsgSeqNumber`) | FIFO per queue, message grouping | **Ordering keys**: FIFO *per key* per region, when the subscription has `enable_message_ordering`. | Throughput per ordering key ≤ **1 MB/s**; a failed ordered publish *pauses* the key until `resumePublish(key)` (the bridge does this). Ordering is only guaranteed with a **single publisher client in one region** per key and for subscribers that ack in order. Key = `storeId` ⇒ ~1 200 independent streams, 1 MB/s each — plenty. Cross-key ordering (e.g. "cancel must follow create across stores") is not provided; use the key that captures the invariant (orderId when stores are irrelevant). |
| **Flow control**: EMS `flowControl` per destination (blocks producers at N bytes), MQ `MAXDEPTH` + `QDEPTHHI` events | `MAXDEPTH`, queue full = `MQRC_Q_FULL` | **Publisher flow control** (client-side: `setFlowControlSettings`, block/throw at N outstanding messages/bytes) and **subscriber flow control** (`maxOutstandingElementCount` = 100 in CONVENTIONS). Backlog is unbounded (up to retention) and priced per byte. | The broker never pushes back on publishers — a runaway producer costs money, it doesn't stall. Alert on `subscription/num_undelivered_messages` and `oldest_unacked_message_age`. Quotas (publisher 240 MB/s per region per project, etc.) are the real ceilings. |
| **Browsing** (`QueueBrowser`, `tibemsadmin show queue`, MQ Explorer browse) | Browse (`MQGMO_BROWSE_*`) | No browse. Equivalents: **BigQuery subscription** (`orders-bq-archive` → `otd.orders_raw`) for "what went through", **snapshots + seek** for "replay from here", a one-off pull with `returnImmediately`-style peek is **not** available (pull always acks or redelivers). | The reconciler browses the EMS audit queue on the legacy side and queries BigQuery on the Pub/Sub side — that asymmetry *is* the concept mapping. Operational "peek at the queue" habits need the BigQuery subscription or the DLQ monitor. |
| **Replay**: EMS has none (once acked, gone; use an audit queue copy); MQ none | — | **`seek`** to a timestamp (needs `retain_acked_messages` + `topic.message_retention_duration`) or to a **snapshot** (7-day lifetime). Pub/Sub keeps acked messages for replay. | Seeking a subscription replays to *all* its subscribers; create a dedicated replay subscription for a consumer and set `source=REPLAY` so downstream can distinguish (ARCHITECTURE §3.1). Replay re-triggers side effects → consumers must be idempotent. |
| **Message groups / exclusive consumers** | `MQGMO_LOGICAL_ORDER` | Ordering keys (above); exactly-once subscriptions for the "only one active consumer" guarantee. | — |
| **Bridges / routes** (EMS routes between servers, EMS–MQ bridge, BW "JMS Queue Sender" to another server) | Channels, remote queues, transmission queues, clustering | **Cross-project** topics/subscriptions (IAM on the resource), **Pub/Sub → BigQuery / GCS / Cloud Storage subscriptions** (no code), **Dataflow** for transformation in flight, and the two bridges in this repo for the legacy edge. | Pub/Sub is global: no transmission queues, no channel status to watch. Cross-org connectivity = IAM + VPC-SC perimeter rules, not network channels. |
| **Fault tolerance**: EMS FT pair (active/standby, shared storage), MQ multi-instance / RDQM / HA clusters | | Regional service, replicated across ≥ 3 zones, 99.95 % SLA; **Pub/Sub Lite** is zonal (avoid for OTD). | No failover for clients to configure (no `tcp://a:7222,tcp://b:7222` URL). Client-side: the library retries with backoff; the bridge's DMLC reconnects every 5 s. Regional outage = the publisher keeps the outbox and the subscriber waits — design for that with the outbox relay. |
| **Admin**: `tibemsadmin`, `tibemsd.conf`, `queues.conf`, `acl.conf`; MQSC (`runmqsc`, `DEFINE QLOCAL`) | MQSC, MQ Explorer, REST admin API | `gcloud pubsub …`, **Terraform** (`google_pubsub_topic`, `_subscription`, `_schema`), Cloud Console. Everything is declarative and version-controlled in `tb-platform-infra`. | No runtime "define queue" by apps: topics/subscriptions are infra (IAM `pubsub.editor` stays with the platform team). The emulator accepts REST calls (`local/pubsub-init.sh`). |
| **Security**: EMS users/groups, ACLs per destination, SSL/TLS + client certs, LDAP; MQ `CHLAUTH`, `SETMQAUT`, TLS channels, `MQCSP` user/password | | **IAM** on topic/subscription (`roles/pubsub.publisher`, `subscriber`, `viewer`), **Workload Identity** (no secrets), **CMEK** for data at rest, **VPC Service Controls** perimeter, audit logs. Transport is TLS always. | Per-message authorisation (EMS "who may send to this queue") maps 1:1 to IAM on the *topic*; "who may receive" maps to IAM on the *subscription*. There is no equivalent to an EMS ACL that filters *which messages* a user sees — that is a separate subscription per audience. |
| **Monitoring**: EMS stats (`show queue`, pending msgs, consumer count), TIBCO Hawk rules/micro-agents, MQ `DISPLAY QSTATUS`, queue depth events | | **Cloud Monitoring** metrics: `pubsub.googleapis.com/subscription/num_undelivered_messages`, `oldest_unacked_message_age`, `ack_message_count`, `dead_letter_message_count`, `topic/send_request_count`, `publisher/…`; alerting policies in Terraform; plus app metrics (`bridge_*` in this repo via Micrometer → Prometheus → Managed Prometheus). | "Consumer count" has no direct metric (use `subscription/open_streaming_pulls` / `num_outstanding_messages` or your own `bridge_running` gauge). "Queue depth" = `num_undelivered_messages` *per subscription*, not per topic. |
| **Message store sizing / disk** (EMS `store` files, MQ log files) | | None — managed. | Costs scale with throughput and backlog bytes, not disk. |

## 2. TIBCO BusinessWorks (BW 5 / BW 6) → GCP

| BW concept | GCP replacement | Notes |
|---|---|---|
| **Process** (orchestration of activities, started by a *process starter*) | **Cloud Run** service (HTTP-started), **Dataflow** streaming job (event-stream processing), **Application Integration** (low-code integration flows w/ connectors), **Workflows** (serverless orchestration of API calls with retries/compensation), **Cloud Functions** for tiny glue | Rule of thumb: stateless request → Cloud Run; stream with windows/joins/enrichment at scale → Dataflow; "BW-like" drag-and-drop with SAP/Salesforce/Oracle connectors → Application Integration; long-running multi-step sagas → Workflows. |
| **JMS Queue Receiver / Topic Subscriber** process starter | Pub/Sub **push** subscription → Cloud Run (`notification-service`), or pull `Subscriber` in GKE (`inventory-service`), or `PubsubIO.read` in Dataflow | Push = simplest scaling, OIDC-authenticated, 600 s max ack; pull = flow control, ordering, exactly-once. |
| **JMS Queue Sender / Publisher** | `Publisher` with ordering + outbox relay | — |
| **Mapper / XSLT / XPath activities** | Dataflow `DoFn`s (Java/Python), Application Integration **Data Mapping** task, Cloud Run code (`LegacyXmlMapper` here: DOM + records, no XSLT) | XSLT is still possible in Java (`javax.xml.transform`) but most teams rewrite to typed code — version-controlled, unit-testable, no BW designer. The XSLT that the SOAP adapter uses lives in `tb-integration-services`. |
| **JDBC palette** (query/update, "JDBC Call Procedure") | Cloud SQL via JDBC in Cloud Run/GKE; Dataflow `JdbcIO`; Application Integration **Cloud SQL connector** | Connection pooling: Cloud SQL Auth Proxy / Java connector. XA with JDBC is gone (see transactions above → outbox). |
| **SOAP palette** (Service Agent, SOAP Request Reply, WSDL) | Cloud Run service with Spring WS (`legacy-oms-soap` simulator, `order-intake-api /ws/orders`), Apigee for SOAP→REST façade | Apigee can front legacy SOAP and expose REST with policies (`XMLToJSON`, `SOAPMessageValidation`). |
| **HTTP palette / REST & JSON plug-in** | Cloud Run + Apigee (API key, quota, spike arrest, OAS validation) | — |
| **File palette** (poll directory, write file) | **GCS** + Eventarc/Pub/Sub notifications → Cloud Run/Dataflow; Transfer Service for SFTP | Polling loops become events. |
| **Timer / Scheduler starter** | **Cloud Scheduler** (→ Pub/Sub, HTTP, Cloud Run Job), **Composer/Airflow** for DAGs (`tb-orchestration`) | — |
| **Shared variables / job shared variables / checkpoints** | Externalised state: Cloud SQL / Firestore / Memorystore; Dataflow state & timers; Workflows variables | BW *checkpoint* (persist process state for restart) ≈ Dataflow checkpointing / Workflows durable execution. |
| **Fault handlers, "Catch" / "Rethrow", retry activities** | Pub/Sub retry policy + DLQ; Workflows `try/retry/except`; Dataflow DLQ `TupleTag` side outputs | Explicit per-service rather than per-activity. |
| **Transaction groups (XA / JDBC / JMS local)** | Outbox + idempotency (see §1) | — |
| **Global variables / deployment profiles (`.substvar`)** | ConfigMaps + Secret Manager + Terraform `tfvars`; Cloud Run env | `MIGRATION_PHASE` is the migration's one global variable. |
| **TIBCO Administrator / AppManage / EAR deployment** | GitHub Actions + Jib + Kustomize/`gcloud run deploy`; Artifact Registry | EAR → OCI image. |
| **Hawk rules & micro-agents** | Cloud Monitoring alert policies, uptime checks, log-based metrics, SLOs | — |
| **TIBCO Adapters (SAP, Oracle Apps, Siebel)** | Application Integration / Integration Connectors (SAP, Oracle, Salesforce…), vendor REST APIs, Datastream for CDC | CDC (Datastream → BigQuery) often replaces "adapter publishes a change event". |
| **EMS as BW's internal bus (`$sys.*`, engine-to-engine)** | Nothing — services talk over HTTP/gRPC or Pub/Sub topics they own | — |

## 3. IBM MQ specifics (the ERP side)

| IBM MQ | Pub/Sub / GCP | Notes |
|---|---|---|
| Queue manager (`QM1`), channels (`DEV.APP.SVRCONN`), listener port 1414, MQ clusters | Project + region; no "manager" concept | The `pubsub-to-jms-bridge` connects in *client mode* (`WMQ_CM_CLIENT`) with `MQCSP` user/password; in production prefer TLS channels with `SSLCIPH` and a `CHLAUTH` rule for the bridge's user. |
| MQMD `MsgId`/`CorrelId` (24-byte binary; JMS maps `ID:` + hex) | `messageId` (string), `correlationId` attribute (string) | Round-tripping `JMSCorrelationID` through MQ keeps it as a byte array; `HeaderMapper` only sets it when it is a non-blank string. |
| Expiry (`MQMD.Expiry`), `MQGMO_WAIT` with interval | Retention + subscriber-side timeouts | — |
| `BackoutCount` / `BOTHRESH` / `BOQNAME` | `delivery_attempt` + dead-letter policy | — |
| MQ transactions / syncpoint; XA with DB2/Oracle | Outbox + idempotent consumers | — |
| `MQRFH2` header for JMS properties | Attributes | `targetClient=1` to drop the header for non-JMS ERP readers. |
| Triggering (`TRIGGER`, initiation queues, trigger monitor starts a program) | Push subscriptions / Eventarc start Cloud Run | — |
| MQ `MAXMSGL` 100 MB | 10 MB | claim-check |
| Publish/subscribe in MQ (topic strings, `SYSTEM.BASE.TOPIC`, retained publications) | Topics; **no retained publications** (last-value cache) | Last-value semantics ("current price") belong in a datastore (Memorystore/Firestore/BigQuery), not in the bus. |
| MQ Explorer / `runmqsc` / `dspmq` | Console / `gcloud` / Terraform | — |

## 4. Quick decision table (for the interview)

| Need | Use |
|---|---|
| Fan-out to N independent consumers | One topic, N subscriptions (never N topics) |
| Competing consumers / scale a worker pool | One subscription, N subscriber clients |
| "Process per store in order" | Ordering key = `storeId`, single publisher per key per region, `enable_message_ordering` |
| "Never process twice" | Exactly-once subscription (pull) **or** idempotent consumer with an inbox table — this platform does both: inbox everywhere, exactly-once on `orders-inventory-service` |
| "Don't lose the DB write when the publish fails" | Transactional outbox + relay |
| "Only consumers interested in cancellations" | Attribute `eventType`, subscription filter `attributes.eventType = "ORDER_CANCELLED"` |
| Priority lane | Separate topic + subscription + consumer pool |
| Big payload | Claim-check (GCS URI in the message) |
| Request/reply | REST/gRPC; if it must be async, reply topic + `correlationId` |
| "What went through yesterday?" | BigQuery subscription (`orders_raw`) / Dataflow tables (`order_events`) |
| Replay after a bug fix | `gcloud pubsub subscriptions seek --time=…` on a dedicated replay subscription, `source=REPLAY` |
| Poison messages | Dead-letter policy → `events-dlq` → `events-dlq-monitor` + alert |
| Broker down (legacy) | Bridges reconnect (DMLC back-off), nothing lost: EMS persists, Pub/Sub retains |
| Who may publish? | IAM `roles/pubsub.publisher` on the topic, Workload Identity, no keys |
